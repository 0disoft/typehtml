# 추가 도구를 설치할 이유부터 확인한다

Boundary Contracts의 설명은 “HTML 폼과 서버 경계의 타입 안전 계약”이다. 입력 검증·인증·객체 권한·공개 응답을 연결하는 래퍼와, 폼이 그 계약과 어긋나는지 확인하는 Doctor를 후보로 둔다. 어떤 모듈을 남길지는 P0에서 결정한다. 보안 사고 감소율·도입률·매출 효과는 측정하지 않았다.

`.thtml`, 새 반응성, 서버 생성기, 일반 정보흐름 분석은 초기 범위 밖이다. HTML label·오류 연결 같은 좁은 검사에는 기존 엔진을 이용한다. 다른 엔진의 진단을 모아 보여주는 기능과 새로운 결함을 발견하는 기능을 분리해서 평가한다.

## 두 가지 도입 경로

| 경로 | 요구하는 정보 | 요구하지 않는 정보 | 제공하려는 가치 |
| --- | --- | --- | --- |
| 폼 연결 검사만 | 입력 schema·codec·고정 제출 대상·검사할 HTML | DB·세션 구현·intent·출력 projector | 기존 서버를 그대로 두고 제출 연결 결함 진단 |
| 실행 래퍼까지 | 위 정보와 역할 바인딩·인증·DB·응답 계약 | 새 UI 언어·별도 라우터 | 등록한 경로의 처리 순서와 공개 투영을 한곳에서 유지 |

검사만 쓰는 경로는 서버를 보호하거나 요청을 차단하지 않는다. 기존 서버의 런타임 검증은 그대로 필요하다. 전체 계약을 쓴 예제에서도 폼 검사 입력은 필요한 부분만 자동 추출한다. 간단한 이름 비교를 하려고 주문 트랜잭션 스펙까지 쓰게 만들지 않는다. [03](03_CONTRACT_AND_SINGLE_SOURCE.ko.md)

## 좁은 지원 범위를 채택 조건으로 공개한다

| 영역 | v0.1 구현 목표 | 현재 산출물 |
| --- | --- | --- |
| 폼 | 고정된 일반 HTML, 평평한 string·integer, URL 인코딩 POST | 계약·정적 스냅샷 |
| 서버 | Hono와 표준 Request·Response를 감싼 실행 래퍼 | 역할 타입 참고안 |
| 저장소 | Bun SQLite, 동일 호스트·단일 파일·동기 트랜잭션 | SQL 참고안 |
| 응답 | 성공 303, 오류 422 HTML, 현재 권한을 확인하는 영수증 GET | 명세·기대값 |
| 스키마 정본 | JSON Schema 또는 지원 부분집합의 신뢰된 정적 투영 | JSON 정본 예제·파생 타입 |
| 분석 범위 | 확인한 폼과 제출 경로, unknown·unsupported 별도 표시 | Doctor 미구현 |

파일·multipart·checkbox 배열·중첩 객체·조건부 필드를 지원하려고 P0를 확대하지 않는다. 실제 대상 프로젝트의 쓰기 폼을 먼저 표본 조사하고, 정적 지원 경로와 막힌 경로를 모두 기록한다. 맞는 폼이 없으면 실험에 맞추려고 사용자 코드를 단순화하지 않는다. 제품 적합성이 없다는 결과를 남긴다.

정식 첫 스키마 지원은 JSON Schema 부분집합이다. Zod·TypeBox를 사용하는 팀에 JSON 수동 복제를 요구하지 않는다. 기존 exporter 산출물의 입력 방향과 손실 여부를 확인할 수 있을 때만 정적 분석에 쓴다. 그렇지 않으면 미지원으로 기록한다. [R13](13_SOURCES.ko.md#r13) [R14](13_SOURCES.ko.md#r14)

## 이제 비교 상대는 래퍼 하나가 아니다

동일 코드에서 B는 기존 타입 검사·validator·typed wrapper, L은 B와 기존 HTML 린터, S는 L과 작은 계약 연결 스크립트, D는 L과 최소 Doctor다. 별도 앱 네 개를 만들지 않는다. 스키마·정책·응답 로직을 공유하고 도구 구성만 바꾼다.

정책 역할 누락은 tsc 대조군으로, 내부 비공개 필드 추가는 projector 대조군으로 옮긴다. 주요 비교는 필수 필드 추가, 유효 제출 경로 변경, 서버 제약과 HTML 제약의 어긋남이다. S가 같은 오류를 같은 시점에 더 적은 관리 비용으로 찾으면 S를 선택한다. D만 발견한 결함도 “이 비교 조건에서 추가 발견”으로 표현한다. 보편적 독점 기능으로 부풀리지 않는다.

추가 발견이 없어도 설정·수정 비용 절감이 반복 확인되면 편의 도구로 남길 수 있다. 그때는 보안 탐지력이 더 높다고 설명하지 않는다. 래퍼도 기존 helper보다 나은지 독립적으로 판단하며, Doctor의 실패가 래퍼 출시를 자동으로 정당화하지 않는다.

## 유지하는 기본 원칙

unknown은 안전 판정에 합치지 않는다. 신뢰해야 하는 callback·DB 어댑터·renderer를 목록으로 공개한다. 실제 성능·시장성 수치가 없으면 미측정으로 남긴다. P0가 끝나기 전에 생성기와 다중 DB·프레임워크 지원을 시작하지 않는다.


## v0.5에서 유지하는 구현 범위

폼 검사기의 최소 동작은 정확한 form binding, 유효 제출 경로, entry 공급·cardinality, 범위가 한정된 반례다. 이를 위해 플랫폼 의미를 명세하지만 checkbox·select·동적 폼을 모두 구현하지 않는다. unsupported를 정확히 출력하는 것으로 초기 경계를 지킨다.

실행 래퍼에는 explicit begin POST, 표시한 revision, 의미 digest, 실제 초안의 intent 유일성을 적용한다. 정적 검사기만 선택한 사용자는 이 runtime 규약을 도입하지 않는다. 새 source를 얻지 못한 채 설계 개정만 반복하는 것을 P0의 성과로 세지 않는다. 다음 단계는 실제 폼 한 개에서 기존 lint 또는 작은 script부터 실행하는 것이다.

이번 수정은 참고 규약의 실제 모순을 제거한다. runtime 상태·DB·타입 보강은 선택적인 P1에 속하고 P0의 선행 조건이 아니다. 다음 개발은 실제 폼 하나에서 기존 도구와 작은 스크립트부터 비교한다. 새 근거 없이 문서를 넓히는 일을 다음 목표로 두지 않는다.
