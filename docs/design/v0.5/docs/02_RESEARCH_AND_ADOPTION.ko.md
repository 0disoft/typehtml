# 기존 도구와 작은 스크립트를 가장 강한 비교 상대로 둔다

새로운 schema 언어나 검증 라이브러리가 필요하다는 근거는 아직 없다. 검증할 가설은 기존 서버를 유지하면서 폼과 서버 사이의 연결을 관리하는 수고가 줄어드는가다. 소개 문구는 “HTML 폼과 서버 경계의 타입 안전 계약”으로 고정하고, 첫 도입 대상은 지원 부분집합의 서버 렌더링 폼으로 제한한다.

## 공식 자료로 확인한 대안

| 대안 | 확인한 기존 기능 | 이번 설계에 주는 결론 | 출처 |
| --- | --- | --- | --- |
| Hono + Zod·Standard Schema validator | form 입력 검증과 typed 결과 접근 | 입력 검증을 Doctor의 독자 기능으로 세지 않는다 | [R26](13_SOURCES.ko.md#r26) |
| Hono RPC | validator 입력과 JSON 응답의 client 타입 연결 | typed 호출의 이득과 원시 HTML 분석을 구분한다 | [R27](13_SOURCES.ko.md#r27) |
| HTML-validate·Markuplint | 중복 폼 이름, label·ID·속성·구조의 여러 검사 | 같은 결함은 기존 lint 성과로 귀속한다 | [R30](13_SOURCES.ko.md#r30) [R31](13_SOURCES.ko.md#r31) |
| 작은 연결 스크립트 | 이 프로젝트가 직접 작성할 비교 구현 | schema와 HTML의 이름 대조만 필요하면 이 구현이 최종 결과여도 된다 | 실험 설계 |
| SvelteKit form actions | JS 없는 POST, 검증 실패·redirect·향상 제출 | 프레임워크 사용자는 해당 흐름을 먼저 활용한다 | [R15](13_SOURCES.ko.md#r15) |
| React Router 계열 action | 서버 action에서 입력 처리·오류 반환·redirect | 기존 Remix 계열 앱의 action을 바꿔야 한다면 도입비에 포함한다 | [R28](13_SOURCES.ko.md#r28) |
| htmx + 서버 검증 | HTML 응답 교체와 브라우저 입력 검증 연계 | 이미 작동하는 제출 UX를 독자 프로토콜로 바꾸지 않는다 | [R29](13_SOURCES.ko.md#r29) |
| Conform | schema의 HTML 제약 추출·입력 속성/접근성 연결 helper | 연결 자체를 생성해 오류를 예방하는 방식도 비교한다 | [R32](13_SOURCES.ko.md#r32) [R33](13_SOURCES.ko.md#r33) |

표는 문서에서 확인한 기능 비교다. 각 도구를 이 ZIP에서 실행해 동일 결함을 탐지한 결과는 없다. Hono RPC가 원시 `<form name>`을 모두 분석한다거나 기존 린터가 외부 업무 schema를 자동 추론한다고 쓰지 않는다. 반대로 기존 도구가 할 수 없다고 단정하기 전 실제 설정·확장 규칙·typed helper를 확인한다.

## 차별화 후보를 기능별로 분해한다

| 가치 후보 | 이미 얻을 수 있는 효과 | 남은 입증 과제 |
| --- | --- | --- |
| 필드 이름·필수 입력 연결 | 작은 schema 비교 스크립트 | 여러 폼·submitter에서 적은 유지비로 연결되는가 |
| 입력 제약 일치 | schema 기반 input helper·기존 제약 추출 | 수작업 HTML을 유지하는 프로젝트에서 도움이 되는가 |
| 오류 위치와 설명 | 기존 lint·tsc의 진단 | 계약 pointer와 실제 폼 위치를 함께 보여주는 편의가 비용을 줄이는가 |
| 처리 순서·투영 | 공용 typed wrapper | 이미 있는 helper보다 중복이 줄어드는가 |
| 우회 인벤토리 | import 검사·프로젝트 스크립트 | 알려진 심볼에서 실용적인 범위를 비용 내에 얻는가 |

Doctor만의 이론적 신기능을 억지로 만들지 않는다. 같은 진단을 덜 설정하고 고칠 수 있다면 통합 편의 가치다. 추가 결함 발견, 더 이른 발견, 관리 비용 절감을 서로 다른 결과로 기록한다. 생성 코드 줄 수·진단 메시지 개수를 가치 점수로 합치지 않는다.

## 도입 전에 맞는 폼이 있는지 조사한다

사용자가 허용한 프로젝트 하나에서 정렬된 route·파일 순서로 쓰기 폼의 제출 경로를 최대 10개 기록한다. 10개 미만이면 전부 기록하고, 이후 경로는 미조사로 표시한다. 쉽게 통과하는 폼만 골라 채우지 않는다. form 개수와 submitter별 제출 경로 개수는 따로 센다. 양식은 [도입 조사](../experiments/adoption-inventory.template.json)에 있다.

각 경로에 정적 HTML 확보 여부, schema 정본, 제출 인코딩, 조건부·배열·파일 여부, response adapter, 기존 검사와 과거 실제 결함 근거를 적는다. Git 기록·이슈·사용자 관찰이 없으면 오류 반복 빈도를 모름으로 남긴다. 합성 결함 3개를 찾았다는 사실에서 실제 사용 빈도나 매출 효과를 계산하지 않는다.

실험 가능한 경로가 한 개도 없으면 미적합으로 종료한다. 비슷한 미지원 요구가 실제 폼 두 개에서 확인되거나, 사용자 지정 첫 출시 기능 하나를 직접 막으면 확장 후보를 하나만 고른다. 숫자 2와 표본 10은 개발 범위 통제용 제안값이다. 시장 조사 수치가 아니다.

## 계약 비용을 줄이는 경로

검사만 쓰는 사용자는 입력 schema·codec·submit 대상과 HTML의 연결만 제공한다. 전체 주문 계약을 쓴 예제에서는 [파생 검사 입력](../examples/form-check.generated.json)을 추출한다. 이 파일을 사람이 유지하는 두 번째 계약으로 만들지 않는다. JSON Schema가 이미 있으면 그 파일과 route/form mapping만 사용한다. 지원 exporter가 없으면 기존 Zod를 JSON으로 다시 쓰게 하지 않는다.

자동 계산값과 사용자가 입력한 값을 분리해 집계한다. 계약·doctor 설정·lint 설정·작은 스크립트·schema bridge·수동 연결·generated 파일을 전부 산출물 목록에 남긴다. 적은 설정을 보여주려고 보안 옵션을 숨기거나 안전하지 않은 기본값을 도입하지 않는다. 전체 runtime profile을 채택하는 결정은 폼 검사 도입과 별도다.

## 현재 선택하지 않는 대상

동적 폼 빌더, 파일 업로드 중심 서비스, 중첩 schema와 transform이 중심인 앱, 이미 typed form helper로 연결을 자동 생성하는 앱은 초기 판매 대상을 좁히는 근거다. 이들에게 기존 프레임워크를 바꾸라고 요구하지 않는다. 사용자 실제 저장소를 이번 개정에서 읽지 않았으므로 제로디님의 모든 서비스에 맞는다고 결론 내리지 않는다.
