# P0에서 기존 도구로 충분한지 먼저 결정한다

P0는 제품을 크게 만들기 위한 통과 의식이 아니다. 기존 검사·작은 스크립트·새 Doctor 중 가장 적은 관리 비용으로 문제를 해결하는 구성을 고른다. 실제 DB·멱등성·다중 프레임워크 구현은 이 판단 뒤에 진행한다.

## 개발 순서

| 단계 | 작업 | 결정에 필요한 증거 |
| --- | --- | --- |
| P0a 적합성 | 실제 프로젝트 쓰기 폼 경로 최대 10개, 기존 도구와 schema 조사 | 지원 가능·미지원·미조사 경로와 도입 장애 |
| P0b 한 경로 비교 | 동일 typed baseline에서 B·L·S·D 구성 비교 | 결함별 최초 발견·도구 공로·수정 비용 |
| P0c 필요한 경우만 확인 | 후보 기능 하나를 두 번째 실제 폼 또는 별도 변경에 적용 | 재사용 이득 또는 반복되는 설정 부담 |
| P1 실행 기능 | 래퍼도 선택된 경우 Hono·SQLite·303/422·GET 한 경로 | 실제 요청·권한·원자성·재응답 |
| P2 선택한 형태 출시 | 기존 lint 설정, 작은 스크립트, Doctor, 래퍼 중 결과에 맞는 것 | 실제 사용 예제·정확한 지원 범위 |
| P3 조건부 생성기 | 반복 수동 연결 하나만 생성 | 현재 선택한 구성보다 편집·관리 부담 감소 |
| 후속 선택 | framework adapter 또는 비동기 DB 중 실제 장애 한 가지 | 해당 프로토콜·트랜잭션을 직접 확인 |

검사만 유용하면 SQLite 구현을 건너뛰고 검사 도구 형태로 출시할 수 있다. 반대로 래퍼만 유용하면 기존 HTML 린터를 사용한다. 각 모듈을 반드시 함께 만드는 일정은 제거한다.

## 하나의 코드, 네 도구 구성

| 구성 | 포함하는 도구 | 비교 목적 |
| --- | --- | --- |
| B | 기존 tsc·validator·typed wrapper/helper | 기존 타입·런타임 효과를 식별 |
| L | B + 이미 쓰거나 선정한 HTML/form lint | 기존 lint 효과를 식별 |
| S | L + 작은 schema/폼 연결 스크립트 | 가장 저렴한 맞춤 구현과 비교 |
| D | L + 최소 Doctor | S 대비 추가 발견 또는 관리 편의 확인 |

모든 구성에 같은 schema·HTML·submitter 정보·기준 commit을 준다. S에도 표준 HTML 파서와 기존 helper 사용을 허용한다. 정규식만 허용하거나 임의 줄 수 상한을 정해 일부러 약하게 만들지 않는다. D가 별도 metadata를 요구하면 S에도 같은 정보를 제공하고, 작성·갱신 비용을 D에 기록한다.

프로젝트에 Hono+Zod 또는 typed form helper가 이미 있으면 B를 그 구조에 맞춘다. 제품이 이기도록 JSON 신규 앱으로 먼저 갈아엎지 않는다. exporter·의미 보존이 막히면 P0a에서 미지원으로 남긴다. 네 앱·네 DB를 만들지 않고 같은 fixture와 실행 기록을 재사용한다.

## 주요 변경과 대조군

[실험 계획](../experiments/p0-plan.json)의 기대값은 구현 가설이며 [결과 양식](../experiments/results.template.json)은 전부 미실행이다.

| ID | 구분 | 변경 | 비교에서 확인할 것 |
| --- | --- | --- | --- |
| C1 | 연결 결함 후보 | 서버에 필수 referenceNote 추가, 기존 폼 유지 | 기존 lint·S·D 중 어떤 구성이 정적 공급 누락을 찾는가 |
| C2 | 연결 결함 후보 | 알려진 제출 route 변경, submitter의 formaction만 이전 경로 유지 | form 자체 action만 보는 스크립트와 차이가 있는가 |
| C3 | 제약 결함 후보 | 서버 수량 최대 20→10, HTML pattern은 11을 허용 | 구체적인 반례 값과 codec까지 설명하는가 |
| N1 | 기존 타입 대조군 | 필수 authorize 역할 제거 | tsc 성과를 Doctor 신규 발견으로 세지 않는가 |
| N2 | 정상 투영 대조군 | 내부 supplierCostMinor 추가, 공개 투영 유지 | 누출이 없는 변경을 Doctor가 잘못 막지 않는가 |
| N3 | 기존 lint 대조군 | 폼 label·접근 가능한 이름 제거 | 기존 엔진의 결함을 통합 표시하되 공로를 가져가지 않는가 |
| G1·G2 | 정상 대조군 | 정상 폼, form 속성으로 연결된 외부 입력 | 실제 제출 의미를 오탐하지 않는가 |
| U1·U2·U3 | 범위 대조군 | 커스텀 직렬화, 조건부 입력, multipart 파일 | unknown·unsupported를 정확히 구분하는가 |

구판 C2는 N1, 구판 C3는 N2로 이동했다. 정책 구현의 의미 오류를 tsc가 모두 찾는다는 주장으로 확대하지 않는다. C3도 임의 정규식의 동치성을 증명하지 않는다. 알려진 정수 codec과 구체적인 반례 11에 한정하고 해석할 수 없는 규칙은 unknown으로 남긴다.

각 변경은 같은 정상 기준에서 독립 적용한다. 변경 diff·정본 해시·도구 버전·옵션·원시 진단을 함께 남긴다. 학습 순서가 시간을 왜곡할 수 있으므로 시간값은 보조 지표로 쓰고 실행 순서도 적는다. 필요한 도구가 없으면 NOT_RUN이며 “놓침”으로 집계하지 않는다.

## 공로와 비용을 함께 기록한다

결함 식별자는 action·submission path·원인으로 정한다. 여러 메시지가 같은 원인을 가리키면 한 결함이다. `engineOrigin`, `originalRuleId`, 발견 단계, 원본 위치, 해당 검사가 실제 실행됐는지 기록한다. tsc·기존 lint 진단을 BC 코드로 포장해도 공로는 원래 도구에 남는다.

동일한 분석 시점에서 B·L·S가 모두 실행됐고 찾지 못한 confirmed 결함을 D가 찾은 경우만 이번 비교의 추가 발견으로 센다. 서버에서만 찾던 결함을 정적으로 찾은 효과는 별도 “발견 시점 개선”이다. 기존 도구가 같은 시점에 찾으면 추가 발견은 0이다. unknown 감소는 증명 가능한 분석으로 confirmed 또는 정상으로 바뀐 경우만 기록한다.

비용은 최초 연결, 변경 후 수정, 경고 확인, 설정·suppressions 유지, 파생물 최신성 확인으로 나눈다. 수동 편집한 필드·파일·연결 위치와 전체 artifact를 센다. 사용자가 실제로 재지 않은 소요 시간은 null로 둔다. 합성 사례의 빈도에 임의 월간 시간을 곱해 ROI를 만들지 않는다.

## 작은 결과로 내리는 결정

| 관찰 | 선택 |
| --- | --- |
| L만으로 같은 결함을 같은 시점에 찾음 | 기존 lint 설정을 남긴다 |
| S가 D와 같은 효과를 더 적은 부담으로 제공 | 작은 스크립트로 끝낸다 |
| D에만 재현 가능한 연결 발견이 있고 정상 대조군을 막지 않음 | 두 번째 실제 경로에서 그 규칙 하나만 확인한다 |
| 추가 발견은 없지만 D의 연결·수정 부담이 반복해서 작음 | 편의 도구로 평가하며 보안 탐지 우위는 주장하지 않는다 |
| 비교 가능한 실제 폼·schema가 없음 | 부적합 또는 판단 보류, 새 기능 자동 확대 금지 |
| tsc·projector 효과만 남음 | Doctor를 중단하고 래퍼도 기존 helper와 독립 비교한다 |

위 기준은 시제품 선택 규칙이다. 통계적 유의성·일반 탐지율을 뜻하지 않는다. 합성 한 건 통과만으로 P1·상용화를 자동 승인하지 않는다. 두 번째 실제 사례가 없으면 국소 가능성만 보고하고 보류할 수 있다.

## 생성기·성능·CI

P3는 현재 선택한 구성에서 반복 수동 연결이 확인될 때만 연다. 생성기 때문에 새 진단이 생겼다고 주장하려면 기존 checker와 분리해 비교한다. AOT가 필요한 배포 환경은 Ajv standalone 같은 기존 수단부터 검토한다. [R25](13_SOURCES.ko.md#r25)

P0 실행 시간은 단일 경로의 최초 분석과 한 번 수정 후 재분석만 원시 값으로 기록한다. 대규모 합성 저장소·브라우저·DB 매트릭스를 만들지 않는다. P1에 들어간 경우에만 실제 HTTP·동시 요청·rollback의 필수 사례를 한 묶음으로 확인한다. 문서 수정에는 자료 검사만 수행하고, 로컬 검증된 커밋을 모아 한 번에 푸시한다.


## v0.5에서도 유지하는 구현 순서

P0b 첫 규칙은 form ID 연결과 required 공급이다. 그다음 submitter의 유효 목적지를 검사한다. C3는 고정 반례 11만 사용하고 범용 solver를 만들지 않는다. 브라우저 참고 probe는 HTML의 동작을 확인한 자료이며 S·D의 탐지 성과에 합치지 않는다.

같은 defect가 실제로 제출 가능한 경로인지 먼저 구분한다. submitter마다 다른 override와 검증 상태를 비교군 모두에 제공한다. BC013 warning도 발견으로 기록할 수 있지만 error 개수를 늘려 유리하게 점수화하지 않는다. 추가 수동 metadata와 start POST로 늘어난 사용자 단계도 비용에 넣는다.

이 설계 패키지의 국소 참고 실행은 P0a를 대신하지 않는다. 다음 작업에 실제 프로젝트가 주어지지 않으면 임의 프로젝트를 만들어 비교 결과로 포장하지 않는다. DB·서버 generator·과도한 교차 브라우저 matrix로 그 공백을 채우지 않는다.

## 이번 설계 이후의 변경 기준

P0의 11사례·4구성은 늘리지 않았다. v0.5의 상태 판정·타입·저장소 참고 확인은 명세 자체의 결함 교정이고 실제 반복 수요의 증거가 아니다. 새 기능은 실제 폼 경로를 막는 구체 사례가 생긴 경우에만 추가한다. 오류가 재현되면 문서를 수정하되, 구현 시작 전에 모든 플랫폼 규약을 완성하려고 기다리지 않는다.
