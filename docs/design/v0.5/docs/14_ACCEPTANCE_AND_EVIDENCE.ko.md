# 자료 확인과 제품 가치 실험을 구분한다

자료의 구조가 맞고 참고 타입이 컴파일돼도 Doctor가 필요한 제품이라는 증거는 생기지 않는다. 이 패키지의 실제 실행은 [검증 기록](../validation/REPORT.ko.md)에만 기록한다. P0·HTTP·Bun 어댑터·브라우저 결과는 미실행이다. 작은 Python WAL 관찰은 별도 참고 증거로만 분류한다.

## 증거 분류

| 분류 | 이번에 확인할 대상 | 확장해서 주장하지 않을 대상 |
| --- | --- | --- |
| ARTIFACT | JSON·상대 링크·정본/파생물·계획/양식 연결 | 실제 앱·시장 가치 |
| WIRE_REFERENCE | 메모리 byte 파서·codec·canonical 입력 | HTTP stream·보안 handler |
| NATIVE_DOM_REFERENCE | 합성 DOM의 선택 사례, v0.4 차단 기록만 이력 보존 | 실제 제출 흐름·앱 coverage |
| REFERENCE_TYPES | 역할 시그니처·9개 타입 거부·넓은 projector의 허용 반례 | 정책 의미·보안 증명 |

## P0 최소 증거

P0a에는 실제 source 범위·조사 순서·발견한 form과 submission path·미지원 원인·미조사 영역을 남긴다. 한 개도 지원되지 않으면 그 자체가 정상적인 종료 결과다. P0b는 같은 baseline과 독립 변경 diff, B/L/S/D별 버전·설정·실행 상태·원시 로그가 필요하다. 기존 도구를 실행하지 않았다면 추가 발견 판정은 보류한다.

C1~C3는 탐지 후보, N1~N3는 공로와 오탐 대조군, G1~G2는 정상 제출 의미, U1~U3는 분석 경계를 확인한다. 합성 계획에 사례를 적은 것은 해당 fixture를 실행한 결과가 아니다. `results.template.json`은 원본 템플릿으로 유지하고, 실제 기록은 복사본에 결과 상태를 바꿔 저장한다.

같은 confirmed 원인을 여러 도구가 출력해도 결함은 한 건이다. D의 추가 발견은 실제 실행한 B/L/S의 같은 시점 결과와 비교한다. 실행되지 않은 구성, 지원 범위가 다른 구성, schema 의미가 다른 구성은 비교 분모에서 분리한다. 진단 화면에서 기존 엔진 출처와 비교 결과를 누락하면 P0 완료로 처리하지 않는다.

도입비에는 전체 runtime contract를 쓰게 하는 비용과 검사 전용 연결 비용을 구별한다. 시간 측정이 없으면 빈 값을 유지하고, 합성 탐지 건수를 실제 월간 절감액으로 바꾸지 않는다. 두 번째 사례가 없는 상태는 국소 확인 또는 판단 보류로 보고할 수 있다. 통과를 만들려고 기능을 늘리지 않는다.

## P1의 최소 수용 조건

| 대상 | 실제로 확인할 한 묶음 |
| --- | --- |
| 네이티브 응답 | GET·intent·정상 303·영수증·오류 422와 같은 intent 수정 |
| 조작 요청 | 미등록·중복·지수 수량·잘못된 CSRF·외부 Origin·초과 스트림 |
| 현재 권한 | 다른 tenant·subject·철회된 회원·영수증 재조회 |
| DB 원자성 | projection 실패 rollback·revision 충돌·동일 intent의 초안 하나 |
| 경합·복구 | 실제 두 연결 writer 경합·503 예산·commit 뒤 응답 유실 |
| intent 수명 | 새로고침·복제 탭·만료·정리·다른 내용 재사용 |
| 공개 화면 | 등록된 공개 값·제한된 raw echo·label/오류 연결 |

모든 조합을 큰 테스트 매트릭스로 늘리지 않는다. 핵심 방어가 실제 실행 경로에서 작동한 자료를 한 묶음으로 남긴다. SQL 참고 예제나 메모리 포트로 두 연결의 DB 경합을 대체하지 않는다.

## 비동기 어댑터는 별도 적합성 기록을 요구한다

후속 PostgreSQL 구현은 같은 transaction client, intent·업무·감사 원자성, 정책 판단과 변경 사이의 동시 수정 방어, commit 불확실성과 재조회, bounded retry를 따로 확인해야 한다. 동기 참고 타입의 tsc 통과로 비동기 구현도 검증됐다고 표시하지 않는다. 현재는 이식 설계만 있다.

## 실행 도구와 의존 버전

문서 패키지는 설치된 도구만 사용하고 정확한 버전을 로그에 남긴다. 환경의 구형 tsc 참고 검사와 제품이 사용할 최신 안정판 호환성을 구분한다. 빠진 도구는 미실행이며 가짜 lockfile을 만들지 않는다. 제품 구현 시 메이저 범위·lockfile·한 번의 필요한 호환성 검사를 함께 적용한다.


## 계속 유지하는 수용 조건

초기 GET/HEAD·자동 미리읽기는 업무 intent를 만들지 않아야 한다. CSRF 보호 begin POST만 발급하며 수량 화면에 표시한 resource revision을 intent에 고정한다. 화면을 본 뒤 가격이 바뀌면 조용히 새 가격으로 처리하지 않고 409로 다시 확인시킨다. 현재 P1 수용은 이 경로까지 포함한다.

source byte hash 변경과 behavior digest 변경을 구분하고, 오래된 계약의 intent는 새 입력 스키마 422보다 먼저 409로 처리한다. 완료 intent의 입력 변경은 409이며 같은 입력의 재응답은 현재 영수증 권한을 확인한다. 실제 draft의 intent 유일성과 결과 참조 FK가 있는지 확인한다.

이번 자료 검사는 wire·상태·URL·동기 반환·JSON과 제한된 Python SQL까지 포함한다. 브라우저 차단은 v0.4 이력이며 v0.5에서는 실행하지 않았다. 합성 DOM 기대값을 실제 관찰로 바꾸지 않는다. 정적 HTML assertion은 브라우저 파서의 모든 복구 의미를 검증하지 않는다. [실제 증거](../validation/REPORT.ko.md)를 기준으로 상태를 읽는다.

## v0.5의 좁은 추가 확인

상태 참고 함수는 OPEN→완료를 새 snapshot으로 관찰했을 때 422가 409로 바뀌는지, 완료 영수증이 상품 가격 변경과 독립적으로 읽히는지, 현재 권한이 없으면 먼저 404인지 확인한다. SQL은 consumed/result 불일치 자료가 자동 정리되지 않는지 확인한다. 두 연결의 Python WAL 관찰은 동시 HTTP 성공이나 Bun 어댑터 완료로 집계하지 않는다.

정본 읽기는 duplicate key·숫자·Unicode 제한을 확인한다. URL 참고 함수는 이미 주어진 속성 사실만 계산한다. 실제 HTML5 파서와 submit 동작은 미구현·미실행 범위로 남는다. 이전 browser 차단 로그를 이번에 다시 시도한 것으로 재사용하지 않는다.
