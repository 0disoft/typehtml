# 후속 연구로 분리한 정보흐름 모델

이 문서는 v0.1 계약·런타임·출시 조건에 포함되지 않는다. OriginSet, ValidationEvidence, GrantScope, Audience를 추적하는 일반 정보흐름 분석은 연구 후보로 남긴다. 신판 계약 JSON에는 이 필드들이 없다.

## 지금 필요한 것과 연구가 필요한 것

현재 구현 목표는 허용된 필드의 디코딩, 서버에서 결정한 principal, 현재 리소스에 대한 정책 호출, revision 조건, 공개 결과 투영이다. 실행 순서를 고정하고 역할 타입과 실제 SQL로 연결할 수 있다. 임의 함수의 값이 어떻게 합성되는지 증명하는 대수는 필요하지 않다.

후속 정보흐름 분석은 값의 유래와 검증 근거, 권한의 객체·작업·시간 범위, 출력 대상의 관계를 다뤄야 한다. `validated`라는 단일 표식으로 SQL·HTML·URL·권한을 한 번에 안전하다고 판단하면 잘못된다. 검증은 특정 문맥의 근거이며 권한은 현재 상태의 관계다.

## 연구를 다시 여는 조건

기존 typed wrapper·정적 진단에서 실제로 놓친 반복 오류가 있어야 한다. 그 오류를 좁은 helper 타입·더 나은 schema·기존 taint 도구로 잡는 기준선과 비교한다. 합성 규칙, 신뢰하는 함수, 출처를 잃는 지점, 명시적 공개 승인, unknown 전파를 작은 언어 부분집합에서 정의하고 soundness 주장의 범위를 문서화한다.

임의 JavaScript·비동기 외부 서비스·반사·동적 코드까지 포함하는 분석은 별도 연구다. 현재 참고 fixture의 opaque Grant는 타입상 실수 방지 장치이며 정보흐름 증명의 결과가 아니다. 이 연구가 시작되어도 `.thtml` 확장자나 새로운 반응성 문법이 필수라고 가정하지 않는다.
